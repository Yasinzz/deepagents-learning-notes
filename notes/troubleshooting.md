这是 [datawhalechina/deepagents-in-action](https://github.com/datawhalechina/deepagents-in-action) 的个人学习记录。以下内容来自本次本机练习与无模型接口验证，不涉及真实模型会话测试。接口验证遇到的问题与学习脚本的实际错误分别标明。

原项目路径统一写作 `<project_root>`。本页只记录错误结构和虚构实验文本，不包含真实偏好、密钥或个人身份信息。完整实验结论见[Task2 主笔记](task2-virtual-filesystem.md)。

## 当前脚本快照：两项尚未整理

### 03_store.py：末尾 if 没有语句体

当前 `<project_root>/practice/vfs/workspace/03_store.py` 第 34 行是 `if read_result_d.error is None:`，后面没有缩进语句体。

只做 AST 解析即可确认 `IndentationError`。Python 会先解析整个文件，所以这不是运行到 D 才失败，而是前面的 A、B、C 实验也不会开始执行。

历史记录中，A/B 共享、C namespace 隔离和 D store 实例隔离的现象已经观察到。但历史输出不能证明当前文件可运行。本次整理没有修复原文件。

后续修正方向：如果要保留成功分支，就补齐该分支的正文读取；如果本轮只需要观察不存在的错误，就移除不需要的条件。修正后先通过语法检查，再验证输出。

### 05_memory_path.py：条件外重复访问 file_data

当前文件第 12–13 行在 `error is None` 时比较正文，第 14 行又在条件外重复比较一次。

读取成功时会重复打印结果；读取失败时，`file_data` 可能为 `None`，无保护访问可能触发 `TypeError`。后者是潜在失败分支，不是已观察到的真实偏好文件读取失败。

后续修正方向：保留成功判断内的一次比较，移除条件外重复语句。本次整理没有修改它。脚本还固定了本机项目位置，分享示例时应改用可配置路径或相对定位，不能照搬个人绝对路径。

## file 与 files 不是同一个状态键

早期普通函数练习使用过 `state["file"]`，输入也提供 `file`，因此函数本身可以运行。但接入 `FilesystemState` 后，框架对应的是 `files`。

修正时要统一输入、节点访问和最终状态访问的名称。普通函数能执行，不代表已经使用了 LangGraph 的状态通道。当前 `02_state.py` 已统一为 `files`。

## StateBackend 不能在普通脚本上下文直接读写

0.7.8 的接口验证表明，`StateBackend()` 的读写需要图执行上下文，缺少它会报 `RuntimeError`。把后端对象放在图外创建并不是根因；真正的边界是读写发生在哪里。

修正方向是将操作放入图节点或工具。先确认节点通过 `compile()` 后的图执行，再加入文件操作。不要根据旧教程改成 `StateBackend(runtime)`；当前版本无参构造。

## 分支外访问局部变量导致 UnboundLocalError

`04_composite.py` 曾在“文件不存在才写入”的条件内给 `result` 赋值，却在条件外执行 `print(result.error)`。

第一次初始化时能运行；同线程第二次调用时跳过赋值，局部变量未定义。即使全局存在同名变量，也不能解决函数内这个问题。

当前文件已把打印放回初始化分支。排查时分别走一次初始化与已有文件两个分支，不能只测试第一次调用。

## 缺少导入或变量定义

接入检查点时曾缺少 `InMemorySaver` 导入、`config` 与 `other_config` 定义，并保留了未定义的 `final_state` 输出。

当前 `04_composite.py` 已补齐导入和两份线程配置，末尾的未定义输出已注释。排查顺序是先解决 `NameError`，再观察后端行为，避免把普通 Python 错误误判为存储问题。

## invoke 返回 None 不等于检查点数据丢失

本机验证中，第一次调用写入文件，第二次以空输入恢复同线程；节点只有读取并返回空字典。第二次 `invoke` 的返回值为 `None`，但节点仍读到了文件。

所以不能无条件对这次返回值执行 `["files"]`。可观察节点读取结果，或通过 `graph.get_state(config).values` 查看保存的状态。这个现象对应本次版本与调用方式，不应扩大成所有只读调用的固定返回规则。

## 节点输入没有自动原地更新

在节点中写入文件后，原先的 `state["files"]` 仍可能保持进入节点时的视图。后端将更新排入状态通道，并没有直接修改这个入参字典。

本机验证中，写后立即调用后端 `read` 能取得新正文，节点结束后的最终状态也包含该文件。不要为了看到变化而手动伪造 `files_update`；0.7.8 的后端已经处理更新。

## namespace 要传函数，单元素元组要有逗号

接口验证中，把固定元组直接传给 `namespace` 可以构造对象，但首次读写会触发 `TypeError: 'tuple' object is not callable`。

正确职责是让函数接收运行时参数，再返回命名空间元组。图外实验采用忽略参数的固定函数。`("vfs-demo",)` 是单元素元组，`("vfs-demo")` 仍是字符串。

相同 namespace 也不能跨新建的 InMemoryStore 自动共享。排查共享问题时，先确认 store 是否为同一实例，再检查 namespace 与文件键；不能只比较后端变量名。

## 混淆外部路径与 Store 中的实际键

Composite 实验中，外部使用 `/memories/note.txt`，底层 StoreBackend 保存 `/note.txt`。直接对底层后端使用完整外部路径，会得到文件不存在。

这不是写入失败，而是路由转换。先确认调用者面对的是 Composite 还是其底层后端，再选择相应路径。图状态的 `files` 也不包含 Store 路由中的文件。

## 替换 backend 后，自定义工具仍写磁盘

项目自定义的报告、来源与偏好工具使用 Path 直接读写，不经过 DeepAgents 后端。更换 backend 后仍看到磁盘产物，不能据此断言后端替换无效。

应沿调用链检查 `read_text`、`write_text`、后端 `read/write` 分别出现在哪里。后端切换也不会自动复制原来的技能文件和记忆文件。

## 文件已更新，已有会话未必重新加载偏好

源码核对显示，MemoryMiddleware 的 `memory_contents` 已存在时，会跳过 sources 的再次读取。`save_preference` 更新磁盘，没有同步刷新该状态字段。

因此要区分“真实文件已写入”“当前状态是否重读”和“模型是否使用了新内容”三项。本次验证覆盖前两项的代码机制，没有完成第三项的真实模型会话测试。

下一次整理时，先修正上述两项待整理脚本，再在不接触敏感文件的测试目录中复现需要验证的现象；记录实际结果，避免用旧输出替代当前检查。
